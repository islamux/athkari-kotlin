الفكرة الحاكمة

Offline-first بنية MVVM

  • • Offline-first: لا شبكة إطلاقاً — لا توجد مكتبات شبكة (README.md:157)
  • • MVVM: UI ← ViewModel ← Repository ← Assets/Preferences (README.md:151)
  • • Activity واحد يستضيف جميع الشاشات عبر Navigation Compose (README.md:154)
  • • ViewModel مخصص لكل شاشة يكشف StateFlow <UiState> (README.md:155)
  • • Repository هو المصدر الوحيد للحقيقة للأذكار (README.md:156)

الفكرة الحاكمة هي offline-first مع انضباط MVVM صارم. الجوهر: UI لا يقرأ البيانات مباشرة، بل يراقب StateFlow. Repository هو مصدر الحقيقة الوحيد. لا توجد مكتبات شبكة إطلاقاً (app/build.gradle.kts لا يحتوي أي network deps).

الغوص التقني العميق

Compose — التركيب الأول مقابل إعادة التركيب

١. التركيب الأول (composition): يُبنى شجر الواجهة مرة واحدة ويُنفَّذ جسم الـ composable لأول مرة.

٢. ماذا يحسب؟ يقرأ القيم المرصودة (قيم StateFlow) ليقرر ما يرسمه.

٣. ما يجب تجنّبه؟ قراءات غير حتمية أثناء التركيب (كقراءة SharedPreferences وسط البناء) تجعل الإطار الأول غير قابل للتنبؤ.

٤. إعادة التركيب (recomposition): تمريرٌ لاحق بإعادة تشغيل الأجسام عند تغيّر الحالة المرصودة — يجب أن تحافظ على نفس شكل الشجرة لئلا تُفقد الحالة (البقاء عبر remember/saveable).

٥. النمط الخاطئ: القراءة من التخزين أثناء التركيب → وميض من الافتراضي إلى المحفوظ، أو تلف الحالة.

٦. النمط الصحيح في المشروع: الـ ViewModel يقرأ الـ prefs مرة واحدة في init ويكشف StateFlow؛ UI يراقب StateFlow فقط؛ والآثار (LaunchedEffect) تعمل بعد اكتمال التركيب.

هذه الشريحة تعيد تأطير مفهوم "hydration/الترطيب" من الويب إلى أندرويد أصلي. جوهرها: إبقاء قراءة الحالة حتمية. التطبيق الفعلي: NotificationSettingsViewModel يقرأ SharedPrefsManager داخل خصائص MutableStateFlow ليست في الـ composable بل في init (NotificationSettingsViewModel.kt:16-32) — أصبحت الحالة حتمية عند أول إطار. الـ UI يجمعها بـ collectAsState، والأثر الوحيد (الجدولة عبر NotificationService) يحدث في دوال المسمّى (setMorningEnabled...) لا في التركيب (:35-53). الآثار مثل LaunchedEffect تعمل بعد الالتزام في Compose.

مقتطف ١ — نمط خاطئ (مبسّط للتوضيح) // ❌ anti-pattern — لا تقرأ الـ preferences داخل التركيب // الإطار الأول = قيمة محفوظة أم افتراضية؟ يعتمد على التوقيت @Composable fun BadToggle() { val prefs = context.getSharedPreferences("athkarix_prefs", MODE_PRIVATE) var enabled by remember { mutableStateOf(prefs.getBoolean("notify_morning_enabled", false)) } // → وميض/عدم تطابق بين الإطار المخطط والفعلي } مقتطف ٢ — النمط الصحيح في المشروع (مبسّط للتوضيح) // ✅ ViewModel يقرأ الـ prefs مرة واحدة في init و يكشف StateFlow class NotificationSettingsViewModel(prefs, service) : ViewModel() { private val _morningEnabled = MutableStateFlow(prefs.morningEnabled) val morningEnabled: StateFlow<Boolean> = _morningEnabled.asStateFlow() // ... init { /* يقرأ الـ prefs مرة واحدة */ } } // ✅ UI يراقب StateFlow فقط (لا يقرأ التخزين) val enabled by vm.morningEnabled.collectAsState()

مقتطف ١ يوضّح anti-pattern: قراءة حقل موحّد داخل جسم الـ composable عبر remember يعتمد على توقيت أول تركيب فلا يمكن التنبؤ بالإطار الأول ويسبب وميضاً. مقتطف ٢ يوضّح نمط المشروع كما في NotificationSettingsViewModel.kt:16-32: يُقرأ prefs في خصائص MutableStateFlow (ثم asStateFlow) فتظهر القيمة الفعلية فوراً، والـ UI يجمعها بـ collectAsState بدون أي قراءة مباشرة للتخزين. دالتي التبديل setMorningEnabled/setEveningEnabled وتحويلات الوقت (كذلك :35-76) تعمل بعد الالتزام وليس أثناء التركيب.

الخاتمة

الخاتمة

القرارات الصادقة أثمن من القرارات المثالية: كل ما بنيناه قابل للتتبّع، وكل ثمنٍ دفعناه مُعلن — وهذا هو أثمن ما نُسلّمه مع الشيفرة.

أسئلة مفتوحة للنقاش:

  • • لماذا اخترنا المحتوى hardcoded في الكود بدل ملفات الأصول؟ — مفاضلة أعلنّاها بوضوح في الشريحة ٩
  • • هل فقدان العدّادات بعد موت العملية مقبول، أم أن الإبقاء ضرورة لا نقاش فيها؟
  • • هل ننتقل من SharedPreferences إلى DataStore؟ وما الطريق الآمن للهجرة؟
  • • هل يستحق الانتقال إلى Hilt ثمنه مع نمو التطبيق؟ — المفاضلة موثّقة في AppModule.kt:22-24

نسأل الله أن يجعل هذا العمل خالصاً لوجهه

الخاتمة مكوّنة من ثلاثة أجزاء: جملة موقفٍ هندسي واحدة (offline-first مع مفاضلات معلنة)، ثم أربعة أسئلة تفتح النقاش مع الجمهور، ثم دعاء ختامي خفيف. الجدول الزمني (الشريحة ٢) يخصص ٥ دقائق لهذا الحوار. اقتراح: اطرح الأسئلة الأربعة كأنها خريطة مغادرة — ليقترح الجمهور أولوية البند الأول في الشريحة ٢٨.
