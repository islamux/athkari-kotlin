Opening

Opening — The Impact

Athkarix is a native Android app (Kotlin + Jetpack Compose) for reading Islamic Athkar (remembrances) and supplications. It is a port from the original Flutter app to Kotlin + Jetpack Compose.

Kotlin 2.2.10 Jetpack Compose MVVM + StateFlow Offline-only Arabic-first RTL

The Impact: a native Android app built with Kotlin + Jetpack Compose. Ported from a Flutter app. Works entirely offline. Golden dark theme. All content is local. Reference: README.md:120 — "It is a Kotlin + Jetpack Compose port of the original Flutter Athkarix app."

Guiding Thesis

Guiding Thesis

Offline-first with MVVM architecture

  • • Offline-first: No network at all — no network libraries (README.md:157)
  • • MVVM: UI ← ViewModel ← Repository ← Assets/Preferences (README.md:151)
  • • Single Activity hosting all screens via Navigation Compose (README.md:154)
  • • Dedicated ViewModel per screen exposing StateFlow<UiState> (README.md:155)
  • • Repository is the single source of truth for Athkar (README.md:156)

The guiding thesis is offline-first with strict MVVM discipline. The core idea: UI never reads data directly — it observes StateFlow. Repository is the single source of truth. There are zero network libraries (app/build.gradle.kts has no network deps).

Technical Deep Dive

Compose — Initial Composition vs Recomposition

1. Initial Composition: The UI tree is built once and the composable body runs for the first time.

2. What determines it? It reads observed values (StateFlow values) to decide what to render.

3. What must be avoided? Non-deterministic reads during composition (e.g., reading SharedPreferences mid-build) make the first frame unpredictable.

5. The wrong pattern: Reading storage during composition → flash from default to saved value, or corrupted state.

6. The correct pattern in this project: ViewModel reads prefs once in init and exposes StateFlow; UI observes StateFlow only; and effects (LaunchedEffect) run after composition completes.

This slide reframes the web concept of "hydration" for native Android. The core: keep state reads deterministic. Actual implementation: NotificationSettingsViewModel reads SharedPrefsManager inside MutableStateFlow properties — not in the composable, but in init (NotificationSettingsViewModel.kt:16-32) — making state deterministic on the first frame. The UI collects via collectAsState, and the only effect (scheduling via NotificationService) happens in named functions (setMorningEnabled...) not during composition (:35-53). Effects like LaunchedEffect run after the composition commit in Compose.

Technical Deep Dive

Compose — Wrong Pattern vs Correct Pattern

Snippet 1 — Wrong pattern (simplified for illustration) // ❌ anti-pattern — do not read preferences inside composition // First frame = saved value or default? Depends on timing @Composable fun BadToggle() { val prefs = context.getSharedPreferences("athkarix_prefs", MODE_PRIVATE) var enabled by remember { mutableStateOf(prefs.getBoolean("notify_morning_enabled", false)) } // → flash/mismatch between planned and actual frame } Snippet 2 — Correct pattern in this project (simplified for illustration) // ✅ ViewModel reads prefs once in init and exposes StateFlow class NotificationSettingsViewModel(prefs, service) : ViewModel() { private val _morningEnabled = MutableStateFlow(prefs.morningEnabled) val morningEnabled: StateFlow<Boolean> = _morningEnabled.asStateFlow() // ... init { /* reads prefs once */ } } // ✅ UI observes StateFlow only (does not read storage directly) val enabled by vm.morningEnabled.collectAsState()

Snippet 1 demonstrates an anti-pattern: reading a unified field inside the composable body via remember depends on timing of the first frame so the first frame is unpredictable and causes a flash. Snippet 2 demonstrates the project pattern as in NotificationSettingsViewModel.kt:16-32: prefs is read in MutableStateFlow properties (then asStateFlow) so the actual value appears immediately, and the UI collects via collectAsState without any direct storage reads. Toggle functions setMorningEnabled/setEveningEnabled and time conversions (lines :35-76) run after composition, not during it.

Process Death & State Recovery

What survives process death?

  • • SharedPreferences persist on disk — 6 notification keys — SharedPrefsManager.kt:38-44
  • • WorkManager queue persists in its own database, so it survives restart — no BOOT_COMPLETED receiver needed due to periodic work — NotificationService.kt:40-49

What does NOT survive?

  • • In-memory StateFlow: Athkar/floating counters not persisted — BaseAthkarViewModel.kt:32-36, FloatingCounterViewModel.kt:8-24
  • • Font size and type not persisted (in-memory only) — FontViewModel.kt:8-40

Integrity point: on process death the user returns to default values for counters and font.

Details: the six keys persisted via SharedPrefsManager are notify_morning_enabled and notify_evening_enabled and notify_morning_hour (default 8) and notify_morning_minute (0) and notify_evening_hour (17) and notify_evening_minute (0) — SharedPrefsManager.kt:37-45. Periodic scheduling via PeriodicWorkRequestBuilder(1 day) with ExistingPeriodicWorkPolicy.UPDATE (NotificationService.kt:40-48) is managed by WorkManager which adds its jobs to a database, surviving restarts without a BOOT_COMPLETED receiver. Meanwhile counters (BaseAthkarViewModel.kt:32-36), floating counter (FloatingCounterViewModel.kt:10-11) and font size/selection (FontViewModel.kt:10-14) are stored in in-memory StateFlow only and are lost. This is an explicitly documented gap.

Trade-offs

Technical Trade-offs

What We Gained

  • • No network dependency — works fully offline (README.md:129-131)
  • • Instant content access: Kotlin constants in memory, zero I/O at runtime (AthkarRepository.kt:6)
  • • Deterministic state flow: UI ← ViewModel ← Repository — single source of truth (README.md:151-157)
  • • Manual dependency injection — dependency graph is visible and traceable (AppModule.kt:22-24)
  • • 52 unit tests: counter, search, settings, font, utilities (eight test files)

What We Paid

  • • Content edits require re-translation — data lives in Kotlin source (data/text/*.kt)
  • • Hand-written lists contain errors: Evening skips TEXT_20 (AthkarRepository.kt:55), Tasbih duplicates TEXT_26 twice (:111, :121), and Salat on the Prophet duplicates TEXT_44 (:217, :256)
  • • Counters are not persisted — lost when the app closes (BaseAthkarViewModel.kt:32-36, FloatingCounterViewModel.kt:8-24)
  • • Font and size not persisted (FontViewModel.kt:8-40)
  • • Search excludes Names of Allah (SearchViewModel.kt:34-45)
  • • Notification channel creation unguarded for API 26 on minSdk 24 (NotificationService.kt:20-29)
  • • No UI tests and no androidTest directory
  • • POST_NOTIFICATIONS permission not requested at runtime — silent on API 33+ (AndroidManifest.xml:4)

Technical trade-offs: the goal is complete transparency — we do not hide what was not resolved. What we gained: no network dependency (README.md:129-131, no network deps in build.gradle.kts), instant access via Kotlin constants (AthkarRepository.kt:6), MVVM discipline (README.md:151-157), visible manual DI (AppModule.kt:22-24), and 52 unit tests. What we paid: content edits require re-translation (data/text/*.kt), hand-written list errors (TEXT_20 skipped by Evening AthkarRepository.kt:55, TEXT_26 duplicated in Tasbih :111 and :121), counters and font not persisted, search excludes assma_hussna, notification channel unguarded on API 24/25, and no UI tests. This is not fragility — it is architectural honesty.
